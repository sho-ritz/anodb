# anoDB のリレー判定基準と定期調査の手順

anoDB の「リレーの自動選定」（docs/DECISIONS.md の 29）で使う**候補の一覧（合格したものすべて、最低 20 個）**を作るための基準と手順です。
定期調査は AI エージェント（muse など）が行い、結果を人間が確認して anoDB の候補の版に取り込みます。

- 判定基準の版: **2**（2: B2 の再試行と無効な日の扱いを追加）（`survey.mjs` の `CRITERIA_VERSION`。基準を変えたら両方を上げる）
- 調査用スクリプト: `survey.mjs`（このフォルダ）
- 結果: `data/`（このフォルダ）

---

## 1. 判定基準

### A. 必須（1 つでも満たさなければ外す）

| # | 基準 | 確かめ方（`survey.mjs` が自動で行う） | 理由 |
|---|---|---|---|
| A1 | 認証・有料・書き込み制限がない | NIP-11 の `limitation` に `auth_required` / `payment_required` / `restricted_writes` が true で**ない** | anoDB は使い捨ての鍵で書くので、ログインも支払いもできない |
| A2 | 初めて見る鍵からの書き込みを受け付ける | 新しく作った鍵で kind 7303 を送り、`OK true` が返る | 封筒は毎回違う使い捨て鍵で署名する。WoT・許可リスト式は使えない |
| A3 | 目印で検索できる | 一度切断してつなぎ直し、`{"kinds":[7303],"#n":[目印]}` で A2 のイベントが返る | anoDB は目印（`n` タグ）でイベントを探す |
| A4 | 時刻の範囲で検索できる | 2 分前の日付のイベントと今のイベントを同じ目印で送り、`since` / `until` で正しく分けて返る | 連番の抜けを、前後の時刻の範囲で探すため |
| A5 | anoDB の最大サイズの封筒を受け付ける | 87,472 文字の content（anoDB の封筒の最大）を送って受け付け、id で取り出せる。NIP-11 の `max_message_length` がある場合は 90,112 以上 | 中身の上限 60 KiB が NIP-44 の詰め物と base64 で約 88 KB になる |
| A6 | 連続書き込みを受け付ける | 1 つの接続から、別々の鍵で 20 件を一度に送り、20 件とも `OK true`（週 1 回の `--burst` のときだけ） | 1 台の端末が毎回違う鍵でまとめて送る |
| A7 | 7 日以上残す | A3 のイベントを「保持の確認用」として記録し、毎日の確認で 7 日以上たっても返る | エポックが変わったあとの猶予期間が 7 日 |

### B. 推奨（点数になる。B2 だけは必須）

| # | 基準 | 目安 | 点数 |
|---|---|---|---|
| B1 | 30 日以上残す | 確認用イベントが 30 日たっても返る | +3 |
| B2 | 毎日動いている | 毎日の確認で、直近 14 回のうち 95% 以上答える（**7 回分たまるまでは「未判定」、95% 未満は外す**）。接続に失敗したら同じ経路で 1 回だけ再試行する。**その日の確認で答えたリレーが 8 割未満なら、調べる側のネットワークの問題とみなし、その日は稼働率の計算に使わない**（保持の記録には使う） | 稼働率 × 4 |
| B3 | 速い | 書き込みの応答の中央値。0.5 秒未満 / 1 秒未満 / 2 秒未満 | +2 / +1 / +0.5 |
| B4 | 一時イベントを中継する | kind 27303 を送ると、別の接続の購読に届く | +1 |
| B5 | NIP-77 に対応 | `NEG-OPEN` に `NEG-MSG` で答える | +1 |
| B6 | 削除依頼に従う | NIP-09（kind 5）を受け付け、対象が返らなくなる | +0.5 |

### C. 候補全体の組み合わせ（一覧を作るとき）

| # | 基準 | 中身 |
|---|---|---|
| C1 | 同じ運営元は 2 個まで | 運営元 = 登録ドメイン（`a.example.com` と `b.example.com` は同じ。共有ホスティングも 1 つと数える） |
| C2 | 同じソフトは一覧の 7 割まで | NIP-11 の `software`（strfry、nostr-rs-relay など） |
| C3 | 同じ地域は一覧の 4 割まで | NIP-66 の geohash の 1 文字目（大まかな地域）。分からないものは数えない |
| C4 | 入れ替えは版ごと | 候補の一覧は版番号つきで人間が取り込む。動き続けているリレーを不必要に入れ替えない |

### 判定の流れ

1. A1〜A7 をすべて満たし、B2 が 95% 以上 → **合格（pass）**
2. 外れる項目はないが、まだ測れていない項目がある（A6、A7、B2 など） → **未判定（provisional）**
3. どれか 1 つでも外れる → **不合格（fail）**
4. 合格したものを**数を決めずにすべて**選ぶ。ただし C1〜C3 は守る。C1 は点数の高い順に見て、同じ運営元の 3 個目から外す。C2・C3 は**できあがる一覧に対する割合**なので、割合を守れる一番大きな一覧になるように、偏ったソフト・地域の点数の低いものから外す
5. 一覧が 20 個に届かない場合は、運営元などの偏りが大きすぎるので、その版は取り込まない

## 2. 定期調査の手順（エージェント向け）

### 準備（最初の 1 回）

```sh
cd anodb/scripts/relay-survey   # このフォルダ
npm install                      # ws と nostr-tools だけ。anoDB のリポジトリ内なら不要
```

Node.js 20 以上が必要です。

### プロキシが必要な環境

出口に HTTP プロキシが必要な環境では、環境変数 `HTTPS_PROXY`（または `HTTP_PROXY`）を設定して実行します。

```sh
HTTPS_PROXY=http://proxy.example:8080 npm run daily
```

- WebSocket（リレー）と NIP-11 の取得の両方が、このプロキシを通ります。TLS はリレーとの間でそのまま暗号化されます（プロキシは CONNECT で中継するだけ）
- プロキシにつながらないときに、**直接接続へ切り替えることはしません**
- プロキシの URL（認証情報を含むことがある）は、画面にもファイルにも書き出しません。記録されるのは「プロキシ経由だったか」（`viaProxy: true / false`）だけです
- プロキシ経由の測定は、速さ（B3）が遅めに出ること、データセンターの IP を拒否するリレーで不利になることがあります。結果を読むときは `viaProxy` で区別してください
- `collect` や `nip11` が 1 件も取れなかったときは、前回のファイルを残したまま止まります（エラー終了）。ネットワークかプロキシの設定を確認してください

### 毎日 1 回（読むだけ。書き込みはしない）

```sh
npm run daily      # = node survey.mjs daily && node survey.mjs select
```

- `daily`: これまでに確認用イベントを書いたリレーすべてに接続し、つながるか（B2）と、確認用イベントがまだ返るか（A7・B1）を記録します → `data/daily/<日付>.json`
- `select`: すべての記録から判定し、候補を選びます → `data/pool/<日付>.json`、`data/pool/<日付>.txt`、`data/evaluation.json`

### 週 1 回（リレーを探し直して、書き込みの試験もする）

```sh
npm run weekly     # = collect → nip11 → check --burst → select
```

- `collect`: NIP-66 の監視記録（kind 30166）と、利用者のリレー一覧（kind 10002）から URL を集めます → `data/urls.json`、`data/geo.json`
- `nip11`: 監視サービスに載っているリレーの NIP-11 を取ります → `data/nip11.json`
- `check --burst`: A1〜A6・B3〜B6 を試し、合格したリレーに確認用イベントを 1 つ残します → `data/checks/<日付>.json`、`data/probes.json`
- 所要時間は全体で 30 分ほどです。

### 報告すること

毎回、`select` が表示するまとめ（`status` / `failedBy` / `selected`）に加えて、次のことを人間に伝えてください。

- 合格数と、前回からの増減
- **前回の候補から外れたリレー**と、その理由（`data/evaluation.json` の `reasons`）
- 確認用イベントが消えたリレー（`daily` の「lost at least one probe」）
- 選ばれた数が 20 に届かない場合は、その旨と主な原因
- C2・C3 で外れた数（`skippedByRule`）が多い場合は、どのソフト・地域に偏っているか

## 3. 守ること

- **書き込みは週 1 回の `check` だけ。** 1 つのリレーに書くのは週に 25 件ほど（試験 5 件＋連続書き込み 20 件）。毎日の `daily` は読むだけです。
- テストの中身はランダムなデータだけ。意味のある文章・個人情報・URL は入れない。
- 拒否されたら、その理由を記録するだけにする。**別の方法で回避しようとしない**（鍵や IP を変えて再試行する、偽の情報を送る、など）。
- 「つながらなかった」は不合格にしない。B2 の稼働率で日数をかけて判断する（`daily` は答えなかったリレーの保持を `kept: null` として扱う）。
- `data/probes.json` を消さない。保持（A7・B1）を測る起点です。
- 判定基準や anoDB 本体の設定（`src/defaults.ts` など）を変えない。候補の一覧を anoDB に取り込むのは人間が行う。
- `data/` 以外のファイルを変えない。git の commit / push はしない。

## 4. ファイル一覧

| ファイル | 中身 |
|---|---|
| `survey.mjs` | 調査スクリプト（collect / nip11 / check / daily / select） |
| `data/urls.json` | 集めた URL と重み（監視記録 3 点、リレー一覧 1 点） |
| `data/geo.json` | URL → geohash（NIP-66 から） |
| `data/nip11.json` | NIP-11 の情報 |
| `data/checks/<日付>.json` | 書き込み試験の結果（A1〜A6、B3〜B6、外れた理由）と `viaProxy` |
| `data/probes.json` | 保持の確認用イベント（60 日で自動的に消す） |
| `data/daily/<日付>.json` | 毎日の確認結果（つながったか、確認用イベントが残っているか）と `viaProxy`・`valid`（稼働率に使うか）・`reachableRatio` |
| `data/evaluation.json` | 最新の判定（全リレー） |
| `data/pool/<日付>.json` / `.txt` | 選ばれた候補と、C1〜C3 で外れたもの（`skipped`） |
| `data/legacy/` | 2026-11-19 の最初の調査（旧スクリプトと結果）。確認用イベントは `probes.json` に引き継ぎ済み |
