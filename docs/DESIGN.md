## 1. 一言で

**anoDB は「端末内の SQLite を正とし、変更を暗号化した Nostr イベントとして既存リレーに流す」Local-first DB の SDK。**
アプリ開発者は API サーバーも DB サーバーもプロジェクト作成もせずに、

- ローカル保存・オフラインでの読み書き
- 同じ所有者の複数端末間の同期（E2EE）
- 他ユーザーの公開データ（プロフィール・投稿）の取得とオフラインキャッシュ
- 既存 Nostr クライアントと互換な公開イベントの発行

を一つの型付き API で使える。

### 名前について

**anoDB = Absolutely None DB** の略。旧称「NoDB（No Database Provisioning）」は既存プロジェクトと衝突するため改名した（npm の `anodb` は 2026-11-09 時点で未使用）。
「Absolutely None」なのは、開発者が用意・運用する DB サーバー／API サーバー／BaaS プロジェクトが**まったく無い**こと。端末内の SQLite や公開 Nostr リレーは使うが、それらは開発者がプロビジョニングするものではない。

### 何ではないか（非ゴール）

| よくある誤解 | 実際 |
|---|---|
| サーバーが一切いらない | Nostr リレー（他人が運営する公開インフラ）を使う。自前で運用しなくてよいだけ |
| 保存が永続保証される | 公開リレーは保存を保証しない。複数リレー・確認応答・ローカル正本で**確率を上げる**だけ |
| 全ユーザーのデータを SQL で検索できる | SQL は**手元に取得済みのデータ**にだけ効く。グローバル検索はインデックスサービスが別途必要 |
| 全端末で強整合なトランザクション | ローカルは ACID。端末間は**結果整合**（セル単位 LWW）。在庫・残高・一意制約のような不変条件は扱えない |
| 削除すれば世界から消える | Tombstone で論理削除するだけ。リレーや他人が持つコピーは消せない |

## 2. 構想メモからの主な変更点

| 構想メモでの論点（§13 未決事項） | v0.1 の決定 | 理由 |
|---|---|---|
| Evolu をフォークするか、新規実装か | **新規実装**。Evolu は設計の参考（セル単位 LWW / HLC / Owner）に留める | Evolu の同期は自前リレー＋RBSR プロトコルに強く結合しており、Nostr ネイティブな「1変更バッチ = 1署名イベント」モデルへの改造量がフォークの利点を上回る。依存（Effect 等）も重い。MIT なので将来部分的に取り込む余地は残る |
| Evolu Relay 互換を保つか | **保たない。Nostr 特化** | 差別化要因が「既存 Nostr ネットワークの利用」なので、二系統を抱える案Aの複雑さを避ける |
| 変更ログの粒度 | **1ローカルトランザクション = 1イベント**（48KB 超は分割） | 1セル1イベントはリレー負荷とイベント数が過大。バッチは暗号化オーバーヘッドも償却できる |
| 競合解決 | **セル（table, row, column）単位の LWW + HLC** | 最も単純で決定論的。カウンタ・集合・テキスト CRDT は将来の列型として追加 |
| スキーマ進化 | **ユーザーテーブルは「射影（materialized view）」で使い捨て**。正本はセルテーブル | 列追加・型変更時は射影を作り直すだけで済む。未知のテーブル/列の変更も保持しておき、スキーマが追いついた時点で表に現れる |
| 公開イベントとの双方向変換 | **kind 0 / 1 / 10002 の読み書き API のみ**。任意テーブル↔公開イベントの自動変換はしない | 変換範囲の設計が未成熟。まずは「プライベート DB」と「標準イベント API」を同じ SDK で提供する |
| リレー探索 | **自分のリレー + 発見用リレー + 相手の NIP-65 write リレー** に問い合わせ、結果を SQLite にキャッシュ | NIP-65 のアウトボックスモデルに従う。網羅性は保証しないことを API の `status` で明示 |
| 保存されない場合の品質保証 | `minAcks`（既定 2）のリレーが OK を返すまで Outbox に残して再送 | 「送った」と「保存された」を区別する |

## 3. アーキテクチャ

```text
┌──────────────────────────────────────────────┐
│ Application                                   │
└───────────────┬──────────────────────────────┘
                │ table().insert/update/delete/findMany/subscribe, sql(), nostr.*
┌───────────────▼──────────────────────────────┐
│ AnoDB (src/db.ts)                             │
│  ├ Schema / 型検証 (schema.ts)                 │
│  ├ HLC 時計 (hlc.ts)                           │
│  ├ 変更 → 暗号化 → 署名 (crypto.ts, protocol.ts)│
│  ├ Outbox / 再送 / minAcks                     │
│  ├ 受信検証 / 復号 / マージ / 追いつき同期        │
│  └ PublicData: kind 0/1/10002 (public.ts)     │
├───────────────────────────────────────────────┤
│ Store (store.ts) ─ SQLite                      │
│  anodb_cells   … 正本（セル単位 LWW レジスタ）    │
│  <user tables> … 射影（クエリ用・使い捨て）        │
│  anodb_events / outbox / acks / cursors / public│
├───────────────────────────────────────────────┤
│ SqliteDriver: node:sqlite / sql.js / 任意       │
└───────────────┬───────────────────────────────┘
┌───────────────▼──────────────────────────────┐
│ RelayPool (relay-pool.ts) ─ NIP-01 over WS    │
└───────────────┬──────────────────────────────┘
          既存の Nostr リレー群
```

**原則**

1. **アプリから見える DB エンジンは一つ**（構想メモの案B）。プライベート・公開キャッシュとも同じ SQLite に入る。
2. **ローカルが正**。ネットワークは「複製の運搬路」であり、オンラインでもオフラインでも書き込み API の挙動は変わらない。
3. **リレーは信頼しない**。署名検証・著者確認・名前空間確認・復号に通ったイベントだけをマージする。
4. **全ての受信は冪等**。同じ変更を何度・どの順序で受け取っても同じ状態に収束する。これが欠落・重複・順序入替・再送・再署名の全てを単純にしている。

## 4. データモデル

### 4.1 セルと射影

全ての変更は `(table, rowId, column, value, hlc)` の **セル更新** に分解される。

- `anodb_cells` は各セルの「現在の勝者」だけを保持する（LWW レジスタ）。HLC が大きい方が勝ち、同じ HLC は重複として無視。
- ユーザーが定義したテーブル（例: `todo`）は、セルから組み立てた **射影**。`SELECT` で自由に読めるが、直接書いてはいけない（`db.sql()` は SELECT/WITH のみ許可）。
- 行の削除は `$deleted = true` セル、作成時刻は `$createdAt` セル。`updatedAt` は行内の最大 HLC の時刻。
- スキーマのテーブル定義が変わると射影を DROP → CREATE → セルから再構築する。

この分離により、**スキーマ不一致の端末同士でもデータを失わない**（古いアプリが知らない列も、セルとしては保存・中継される）。

### 4.2 HLC（Hybrid Logical Clock）

`<millis:base36 10桁><counter:base36 5桁>-<nodeId:hex16>` の固定長文字列。文字列比較 = 時刻→カウンタ→ノード ID の順序。

- 端末ごとにランダムな `nodeId` を生成し SQLite に保存（同時刻のタイブレーク）。
- 受信した最大 HLC で時計を進めるため、「受信後の自分の書き込み」は必ず受信内容より新しい。
- 壁時計が戻っても単調増加。

**注意:** 端末の時計が大きく未来にずれていると、その端末の書き込みが長期間勝ち続ける。v0.1 では拒否せず受け入れている（拒否すると端末間で収束しなくなるため）。将来、許容ずれを超えた変更を警告する。

### 4.3 型

`text | integer | real | boolean | json`。全列 nullable（セルは独立に到着するので、行の一部の列だけが先に届くことがある）。
受信値が宣言型と合わない場合（スキーマずれ）は射影上 `NULL` になり、セルには元の値が残る。

## 5. 同期

### 5.1 書き込み（ローカル → リレー）

1. `transaction()` 内の書き込みを型検証しながらセル変更列に変換（各セルに HLC 付与）。
2. 変更列を 48KB 以下に分割 → NIP-44 v2 で**自分自身宛て**に暗号化 → kind `7303` イベントとして署名。
3. **1つの SQLite トランザクション**で「セル適用・射影更新・HLC 保存・イベントを既読登録・Outbox 投入」を行う。途中で失敗すれば全てロールバック。
4. 接続中のリレーへ送信。各リレーの `OK` を `anodb_acks` に記録し、`minAcks` 件の成功で Outbox から外す。
5. 失敗・未接続のリレーには、再接続時と `retryIntervalMs` ごとに再送。全リレーが拒否した場合は `publish-rejected` エラーを出し、`db.sync()` で再試行できる。

**再署名:** オフラインで書いたイベントは `created_at` が古いまま後からリレーに届く。他端末は `since` カーソルで購読しているため、古い `created_at` のイベントを見落とし得る。そこで **5分以上 Outbox に滞留した変更イベントは、同じ暗号文のまま新しい `created_at` で再署名**して送る。受信は冪等なので、旧イベントと新イベントの両方が届いても問題ない。

### 5.2 受信（リレー → ローカル）

購読フィルタ: `{ kinds:[7303], authors:[owner], "#n":[namespace], since: cursor − 600秒 }`

各イベントに対して:

1. kind・著者・名前空間タグを確認 → 既読ならスキップ。
2. サイズ上限・Schnorr 署名を検証。
3. 復号 → ペイロードの形とプロトコルバージョンを検証。未知バージョンは**既読にしない**（将来のバージョンが `resync()` で読めるように）。
4. HLC を進め、1トランザクションでセルをマージ → 既読登録。
5. 変更されたテーブルの購読者に通知。

### 5.3 追いつき（バックフィル）

リレーは 1 REQ で返す件数に上限がある（数百件など）。EOSE を受けたら、受信した最古の `created_at` を `until` にしてページングで遡り、**新しいイベントが1件も来なくなるまで**続ける。完了して初めてリレーごとのカーソルを進めるため、途中で終了しても次回やり直せる。

**既知の限界:** NIP-01 は秒より細かくページングできない。同じ1秒間にリレー上限を超える件数のイベントがあると、その秒の一部を取りこぼす可能性がある（その秒は飛ばして古い方へ進むので、詰まることはない）。根本解決は NIP-77 Negentropy（v0.3 予定）。

### 5.4 状態

`db.status` = `{ state: 'offline' | 'syncing' | 'synced', connectedRelays, pendingEvents }`

- `offline`: 接続中リレーなし（読み書きは普通にできる）
- `syncing`: 追いつき中、または Outbox に未確認イベントあり
- `synced`: 接続中の全リレーに追いつき済みかつ Outbox が空

## 6. 公開データ（Nostr 互換）

| API | イベント | 備考 |
|---|---|---|
| `nostr.getProfile(pubkey)` | kind 0 | キャッシュ → 自分のリレー + 発見用リレー + 相手の NIP-65 write リレー |
| `nostr.cachedProfile(pubkey)` | kind 0 | ネットワークに触れない |
| `nostr.getRelayList(pubkey)` | kind 10002 | NIP-65 |
| `nostr.getNotes(pubkey)` | kind 1 | 相手の write リレーも探索 |
| `nostr.publishProfile / publishNote / publishRelayList` | 0 / 1 / 10002 | Outbox 経由で確実に送信 |
| `nostr.fetch(filters)` | 任意 | 署名検証済みのイベントのみ返す |

取得結果は `status` を持つ:

- `synced`: リレーから取得できた（または鮮度内のキャッシュ）
- `stale`: リレーから取れなかったがキャッシュを返した
- `unavailable`: どこにも無い（リレーが消した・リレーが分からない・存在しない）

相手本人がオフラインでも、どこかのリレーにイベントが残っていれば取得できる。

## 7. セキュリティとプライバシー

### リレーから見えるもの / 見えないもの

| 見える | 見えない |
|---|---|
| 所有者の公開鍵、書き込み時刻（秒）、イベントのおおよそのサイズ（NIP-44 のパディング後） | テーブル名、列名、値、行 ID、appId（名前空間タグは `sha256(appId, pubkey)` のハッシュ） |
| 同じ所有者・同じアプリのイベント群であること | どの行が何回更新されたか |

### 鍵

- v0.1 は **所有者鍵 = Nostr ID 鍵** の1本。`secretKey` を渡さない場合は生成して SQLite に**平文で**保存する（端末のディスク暗号化に依存）。
- 複数端末は `db.exportSecretKey()`（nsec）を別端末で `secretKey` に渡して共有。
- 同じ鍵で公開投稿も行うため、「この公開鍵の人は anoDB アプリを使っている・いつ書き込んだか」は推測できる。プライバシーを重視する場合は、公開用と DB 用で別の鍵を使う（v0.2 で `identityKey` を分離予定）。
- NIP-44 の自己宛て暗号は前方秘匿性を持たない。鍵が漏れると過去の全データが読める。

### 信頼境界

署名が正しいことは「所有者が書いた」ことしか意味しない。v0.1 は所有者 = 単一主体なので、署名検証がそのまま権限検証になる。複数参加者の共有（v0.2）では、署名とは別にアプリの権限ポリシー検証が必要になる。

## 8. 未解決の課題と対応方針

| 課題 | v0.1 の状態 | 今後 |
|---|---|---|
| 永続性 | 複数リレー + minAcks + ローカル正本 | 有料/専用リレーの指定、定期的な「自分の全イベントが各リレーにあるか」の監査 |
| リレー間差分 | `since` + バックフィル + 再署名 | NIP-77 Negentropy で差分照合（非対応リレーは現方式にフォールバック） |
| ログの肥大化 | 全変更イベントを保持 | スナップショットイベント + 古いイベントの NIP-09 削除要求（リレーが従う保証はない） |
| 共有（複数人） | 未対応（所有者のみ） | グループ鍵（NIP-44 で各参加者に配布）、書き込み権限を持つ pubkey 集合、鍵ローテーション。取消後も過去データは回収できないことを API で明示 |
| 型別マージ | LWW のみ | カウンタ（端末別加算）、集合（追加/削除の OR-Set）、テキスト CRDT |
| ブラウザでの永続化 | sql.js（メモリ）または同期 VFS の SQLite を自前で用意 | sqlite-wasm OPFS ドライバを同梱、Worker 実行 |
| 大きなデータ | 1セル 48KB まで | Blossom に blob を置き、セルにはハッシュ参照 |
| グローバル検索 | なし | 範囲を明示した外部インデックス連携 |
| 時計ずれ | 受け入れて警告なし | 許容ずれ超過の検出と警告 |
| スパム | 自分の鍵のイベント以外は無視 | 共有時のレート制限・サイズ制限 |

## 11. 暫定結論（改訂）

構想メモの仮説「Local-first DB 体験を Nostr の公開ネットワークに接続する」は、**単一ローカルエンジン（案B）で、所有者1人・複数端末の範囲なら成立する**ことを v0.1 で確認した。鍵になったのは次の3点:

1. **正本をセルテーブルに置き、ユーザーテーブルを射影にする**ことで、スキーマ進化と順不同受信を単純化できた。
2. **受信を完全に冪等にする**ことで、リレーの欠落・重複・再送・再署名をすべて「もう一度送る」で解決できた。
3. **「送信済み」と「保存確認済み」を分ける Outbox** が、公開リレーの不確実性に対する現実的な答えになる。

残る最大の課題は、**複数人共有の権限と鍵配布**、**ログ肥大化**、そして**公開リレーの保存が保証されないというプロダクト上の限界**である。
