## 1. 一言で

**anoDB（Absolutely None DB）は「端末内の SQLite を正とし、変更を暗号化した Nostr イベントとして既存リレーに流す」Local-first DB の SDK。**
開発者が用意・運用するサーバー（DB・API・BaaS プロジェクト）は**まったく無い**。

- SQL ライクで型安全な API（Kysely）と、生 SQL の書き込み互換
- オフライン読み書き・複数端末同期・**複数人での共有（役割・招待・権限取り消し）**
- **既定で最も強いセキュリティ**（端末鍵・暗号化保存・メタデータ秘匿・鍵の定期更新）
- 公開 Nostr データ（プロフィール・投稿・フォロー等）を**SQL のテーブル**として読み書き

### 非ゴール（できないこと）

| 誤解 | 実際 |
|---|---|
| サーバーが一切無い | 他人が運営する公開 Nostr リレーを使う（自分で用意しないだけ） |
| 保存が永続保証される | 公開リレーは保証しない。複数リレー・確認応答・ローカル正本・修復で確率を上げる |
| 世界中のデータを SQL で検索 | SQL は**手元に取得したデータ**にだけ効く |
| 端末間で強整合 | 結果整合（セル単位 LWW）。在庫・残高・一意制約は不可 |
| 削除すれば消える | Tombstone（論理削除）。他人やリレーが持つコピーは消せない |
| 取り消せば過去も読めなくなる | 外した人が**外される前に読んだデータ**は回収できない |

## 2. アーキテクチャ

```text
┌────────────────────────────────────────────────────────────┐
│ App ── Kysely API / db.execute(SQL) / useQuery (anodb/react) │
└──────────────────────────┬─────────────────────────────────┘
┌──────────────────────────▼─────────────────────────────────┐
│ AnoDB (anodb.ts)   NIP-77・欠落検出/修復・prune・公開テーブル      │
│  └ AnoDBSharing (sharing.ts)  スペース・役割・招待・鍵更新・      │
│       スナップショット・QRペアリング・端末失効                    │
│     └ AnoDBCore (db.ts)  鍵/委任・書き込み捕捉・封筒・受信検証     │
├────────────────────────────────────────────────────────────┤
│ capture.ts  TEMP トリガーで「どのセルが変わったか」を捕捉          │
│ membership.ts  署名付き操作の DAG から権限状態を決定的に評価       │
│ Store (store.ts) ─ SQLite                                    │
│   anodb_cells     正本: (space, table, row, col) の LWW        │
│   <user tables>   射影（読み取り用・使い捨て、PK = (space,id)）  │
│   anodb_messages  受理した全メッセージ（再評価用）               │
│   anodb_raw / outbox / acks / cursors / devices / invites …  │
├────────────────────────────────────────────────────────────┤
│ KeyStore: browser(IndexedDB+非抽出鍵) / env / Electron / Expo │
│ Signer:   local / NIP-07 / NIP-46 / NIP-55                    │
│ SqliteDriver: node:sqlite / sql.js(+IndexedDB) / expo-sqlite  │
└──────────────────────────┬─────────────────────────────────┘
┌──────────────────────────▼─────────────────────────────────┐
│ SyncEngine + RelayPool: NIP-01 購読・ページング・Outbox・NIP-77 │
└──────────────────────────┬─────────────────────────────────┘
                    既存の Nostr リレー群
```

**原則**

1. **アプリから見える DB エンジンは一つ**。個人・共有・公開データが同じ SQLite に入り、JOIN できる。
2. **ローカルが正**。ネットワークは複製の運搬路。オンラインでもオフラインでも書き込みの挙動は同じ。
3. **リレーも他のメンバーも信頼しない**。署名・委任・権限・世代鍵をすべて受信側が検証する。
4. **受信は完全に冪等**。重複・順不同・再送・再署名・後から届く権限変更のすべてを「再評価」で吸収する。
5. **既定は最も安全な設定**。弱める選択肢は名前で明示（`metadataProtection: 'none'` など）。

## 3. 鍵と ID

| 鍵 | 役割 | 既定の置き場 |
|---|---|---|
| **本人の鍵（identity）** | 端末の委任・失効、鍵パッケージ、公開イベントの署名 | セキュアストレージで暗号化（`identity: 'recovery'` なら端末に置かない） |
| **端末鍵（device）** | 全ての書き込みメッセージの署名 | セキュアストレージ / Node は環境変数 |
| **世代鍵（epoch key）** | スペースの暗号化。世代ごとに別 | SQLite に**キーストアで封印して**保存 |

- 本人の鍵は「この端末鍵は私の代理」という**委任**（kind 7304）に一度だけ署名する。以後の書き込みは端末鍵だけで行うので、外部署名者（NIP-07/46/55）を使ってもオフラインで書ける。
- 端末が乗っ取られても漏れるのは端末鍵（と、その端末が読めたデータ）。端末を**失効**させればそれ以降の書き込みは全員に拒否され、鍵も更新される。
- **全端末を失うと個人スペースは復元できない**（世代鍵は端末鍵宛てにしか渡さないため。セキュリティ優先の決定）。共有スペースは他のメンバーから戻れる。

### 環境ごとの既定

| 環境 | キーストア | 備考 |
|---|---|---|
| ブラウザ / Tauri | IndexedDB ＋ 取り出し不可の WebCrypto AES 鍵 | ディスク盗難に強い。XSS で「使われる」ことは防げない |
| Node | 環境変数（`ANODB_DEVICE_KEY` / `ANODB_DELEGATION`） | `npx anodb init` が生成。本人の鍵は `.env` に書かず復元用キーとして表示 |
| Electron | `electronKeyStore(safeStorage)` | OS キーチェーン |
| React Native / Expo | `secureStorageKeyStore(expo-secure-store)` | |
| テスト | `memoryKeyStore()` | |

## 4. データモデル

- 全ての書き込みはセル更新 `(space, table, rowId, column, value, hlc)` に分解され、`anodb_cells` で **HLC の大きい方が勝つ**。
- ユーザーテーブルは射影。`space`, `id`, `createdAt`, `updatedAt` が自動で付き、**主キーは (space, id)**。スキーマが変わると作り直してセルから再構築する。
- 削除は `$deleted` セル（tombstone）。
- 型: `text | integer | real | boolean | json`。SQLite の流儀どおり boolean は `0|1`、json はテキストで読む。

### 書き込みの捕捉（SQL 互換）

ユーザーの SQL（Kysely が生成したものも生 SQL も）は、射影テーブルに対して**そのまま SQLite で実行**される。TEMP トリガーが変化したセルを記録し、射影の変更はロールバックされたうえで、記録したセルが正規の経路（型検証 → 権限確認 → HLC → 暗号化メッセージ → Outbox）を通る。SQLite 自身が SQL を解釈するので、`UPDATE … WHERE … LIKE`、`INSERT … SELECT`、`ON CONFLICT DO UPDATE`、`RETURNING` が使える。複数文のトランザクションは原子的（中の読み取りは自分の書き込みを見る）。

## 5. スペースと共有

個人データも「メンバーが自分1人のスペース」。スペース ID は `sha256(owner, nonce)` で所有者に結び付いているので、他人が `create` を偽造できない。

### 役割

| 役割 | 読む | 書く | 招待・削除・役割変更 |
|---|---|---|---|
| owner（1人） | ✅ | ✅ | ✅（admin も） |
| admin | ✅ | ✅ | ✅（writer / reader のみ） |
| writer | ✅ | ✅ | ❌ |
| reader | ✅ | ❌ | ❌ |

### メンバー表 ＝ 署名付き操作の DAG

各操作（add / role / remove / leave / transfer / revoke）は、作者が見ていた操作の ID を親として参照する。**操作は「その祖先だけから作った状態」で作者に権限があったときに限り有効**。全端末が同じ規則で評価するので、順番に関係なく同じ結論になる。

- **削除は、同時に起きた（子孫でない）追加・役割変更に勝つ**（安全側）
- 上位の役割が優先（owner は外せない）
- **カットオフ**: 削除・降格・端末失効の操作は「端末ごとの通し番号のここまでは受け入れる」を含む。それより後の書き込みは拒否されるので、**日付の偽装は効かない**。同時に2つのカットオフがあれば小さい方を採用する
- 権限が後から判明しても大丈夫なように、受け取った全メッセージを保存し、メンバー表が変わるたびにスペースを再評価する

### 招待

| 方法 | 流れ |
|---|---|
| npub 招待 | 相手は鍵パッケージ（kind 10304: 端末の委任一覧）を公開しておく → admin が `invite(space, npub, role)` |
| 招待リンク | 使い捨て・期限付きのリンク → 開いた人は「参加リクエスト」を送るだけ → **admin が承認**して初めて鍵が渡る |

どちらも**招待された側が承諾するまで何も同期されない**（自分で送ったリクエストへの招待は自動承諾）。

### 世代鍵の更新とスナップショット

- 更新のタイミング: **メンバー削除・端末失効・メンバー追加・30日ごと**（脱退は owner が更新）
- 新しい鍵は、残る全メンバーの全端末の受信箱に個別に暗号化して届ける
- 更新の直後に、新しい世代で**現在状態のスナップショット**を投稿する
- 新メンバー・新端末には**新しい世代の鍵とスナップショットだけ**が渡る。過去の編集履歴や**削除済みの内容は渡らない**（スナップショットの削除行は tombstone のみ）
- 書き込みが 1000 件たまるごとにも自動でスナップショットを作る

### 端末の追加（QR ペアリング）と失効

新しい端末が QR（端末公開鍵＋使い捨ての秘密）を表示 → 既存の端末が読み取り、両方に表示される6桁コードを目で照合 → 既存端末が本人の鍵で委任に署名し、各スペースの鍵とスナップショットを渡す。**本人の鍵はコピーしない**。

## 6. メタデータ秘匿

リレーに出るのは**封筒**（kind 7303）だけ。

- 外側の署名は**イベントごとの使い捨て鍵**（誰が書いたか分からない）
- ルーティングタグは**世代鍵から導出**され、鍵の更新で変わる（外部の人は長期間の追跡ができない）
- 中身（NIP-44 v2）に端末鍵で署名した本当のメッセージと委任が入っている

リレーから見えるのは「使い捨ての公開鍵・タグ・時刻・サイズ」だけ。登録制の有料リレー向けに `metadataProtection: 'none'`（端末鍵で外側を署名）を用意する。

## 7. 同期（4層）

| 層 | 仕組み | 弱点を補う相手 |
|---|---|---|
| ① **NIP-77 Negentropy** | 封筒 ID 集合を突き合わせ、足りない分だけ取得し、リレーが失った自分の封筒は**再アップロード** | 対応リレーのみ（例: offchain.pub）。非対応は NOTICE / 無応答で判定 |
| ② 時刻ベース | タグごとのカーソル − 600 秒で購読、EOSE 後に `until` で遡る | 同じ1秒にリレー上限を超えると取りこぼす |
| ③ **通し番号による欠落検出** | 端末ごとの `seq` の抜けを検出し、全リレーから深く取り直す（`db.repair()`）。`db.syncHealth()` で可視化 | ②の取りこぼしが**黙って起きない**ようにする |
| ④ スナップショット | 新端末・新メンバーはスナップショット＋以降だけで追いつく | 履歴全体を取らなくてよい |

- 書き込みは Outbox に入り、`minAcks`（既定2）のリレーが OK を返すまで再送。5分以上滞留した封筒は新しい `created_at` で再署名（中身は同じ）
- ③の限界: NIP-77 非対応のリレーしか無く、同じ1秒にリレー上限を超えるイベントがある場合、**欠落は検出できるが、そのリレーからは取り戻せない**（NIP-01 は秒より細かくページングできず、封筒の著者は使い捨てなので `authors` でも絞れない）。他のリレーか NIP-77 で回復する
- `pruneOldEvents: true` にすると、スナップショットより古い自分の封筒について NIP-09 削除依頼を出す（封筒の鍵は端末鍵＋ソルトから導出するので、秘密を追加で保管しない）。既定はオフ

## 8. 公開テーブル（Nostr 互換）

```ts
defineSchema({ posts: publicTable('note'), profiles: publicTable('profile'), follows: publicTable('follows') })
```

| プリセット | kind | 行 | 更新 |
|---|---|---|---|
| `note` | 1 | 1 イベント = 1 行 | 編集不可（削除＝NIP-09） |
| `profile` | 0 | 作者ごとに 1 行（`id` = pubkey） | 置換（新しい方が勝つ） |
| `follows` | 3 | フォロー先ごとに 1 行 | 自分の行の増減 → リスト全体を再発行 |
| `reaction` | 7 | 1 イベント = 1 行 | 削除＝NIP-09 |
| `longForm` | 30023 | `d` ごとに 1 行 | アドレス単位で置換 |

- `INSERT/UPDATE/DELETE` は**本人の鍵で署名された標準イベント**になり、他のクライアントからそのまま見える（recovery モードでは署名者が必要）
- `db.syncPublic(table, filter, { live })` で取得（署名検証済み・置換規則つき）してローカルに保存 → オフラインでも SQL・JOIN できる。著者を指定すると NIP-65 の write リレーも探す
- 公開テーブルは**暗号化されない**。置換イベントの自分の更新は、既存より必ず新しい `created_at` にする（同秒の「id が小さい方が勝つ」規則で編集が負けるのを防ぐ）

## 7.5 端末間の直接同期（WebRTC）

リレーは「保管と、オフラインの相手への配達」、WebRTC は「オンライン同士の即時配達」と役割を分ける（[nostr-p2p](https://github.com/sho-ritz/nostr-p2p) を使用）。

- **ルーム**: スペースごとに、世代鍵から導出した名前の nostr-p2p ルーム（`transport: 'direct'`）に入る。鍵を知るメンバーだけが見つけられ、鍵の更新で外されたメンバーは新しいルームに入れない
- **端末の証明**: 接続直後に、端末鍵で `"<roomId>:<相手のセッション鍵>"` に署名した証明を交換し、そのスペースの有効な端末（失効していない）だけを相手にする
- **配達**: 新しい封筒はまず接続中の端末へ直接送る。受け取った側は通常と同じ検証（署名・復号・権限）をしてから ack を返す
- **リレーを省く条件**: スペースの**全端末**が直接つながっていて、2 秒以内に全員が ack したときだけ、その封筒をリレーに送らない（ローカルでも「リレーに無い」印を付け、NIP-77 で再アップロードしない）。それ以外はリレーにも送る
- **既定**: 自分の端末同士だけ（`own-devices`）。他のメンバーとの直接接続（`members`）は IP アドレスが相手に見えるためオプション
- ブラウザ同士の実測: 直接接続まで約 2 秒、変更の到達 約 50ms（リレー経由は約 0.5〜1 秒）

## 8.5 ファイル（Blossom）

1 セルは約 44KB までなので、ファイルは Blossom サーバー（Nostr エコシステムのファイル置き場、HTTP）に置く。

1. 端末でランダムな鍵を作り、**AES-256-GCM で暗号化**
2. 暗号文を複数のサーバーに `PUT /upload`（BUD-02）。認可は kind 24242（BUD-11、Base64url、`server` タグでそのサーバー専用）を**ファイルごとの使い捨て鍵**で署名。鍵は `sha256(端末鍵, ソルト)` から導出するので、アップロードした端末だけが後で削除（BUD-12）できる
3. DB には参照 `{ sha256, size, type, key, servers, salt }` を `json` 列として保存 → 通常の値と同じく E2EE で同期され、メンバーだけが復号できる
4. 取得時は sha256 を検証してから復号（改ざん検出）。失敗したら別のサーバーを試す

公開サーバーの多くは画像・動画しか受け付けず、暗号文（application/octet-stream）を拒否する（2026-11-10 時点で 16 台中 3 台のみ受け付け）。Content-Type を偽る回避はしない。保存の保証も無いので、確実に残すには自前・有料サーバーを `blobServers` に足す。

## 9. 脅威モデル（まとめ）

| 攻撃者 | 防げること | 防げないこと |
|---|---|---|
| リレー運営者 | 内容・テーブル名・作者・スペースの所属の秘匿、改ざん検出 | 保存の拒否・削除、時刻とサイズの観測 |
| 外部の第三者 | 偽造（署名）、スペースへの投げ込み（タグは秘密から導出） | DoS |
| 外されたメンバー | 以後のデータの閲覧（鍵更新）、以後の書き込み（カットオフ）、日付の偽装 | 外される前に読んだデータの保持 |
| 端末の盗難 | 本人の鍵の保護（セキュアストレージ / recovery）、失効による遮断 | その端末で読めたデータの閲覧 |
| 悪意ある writer | reader への昇格・権限操作（admin のみ） | writer 権限の範囲での書き換え（スナップショット経由を含む） |
| ページ上の XSS | ― | 開いている間の鍵の使用 |

ローカルの SQLite 自体は暗号化していない（射影とセルは平文）。ディスク暗号化に依存する。

## 10. 既知の制約と今後

| 項目 | 状態 |
|---|---|
| 1 セルの大きさ | 約 44KB まで。大きなデータは `db.blobs`（Blossom）に置いて参照する |
| ブラウザの永続化 | sql.js のイメージを IndexedDB に保存。OPFS ドライバは未実装 |
| 前方秘匿性 | 世代鍵の更新による区切りのみ（MLS 級ではない） |
| 型別 CRDT | LWW のみ（カウンタ・集合・テキスト CRDT は未実装） |
| 時計ずれ | 未来の HLC を受け入れる（警告なし） |
| kind 番号 | 7303 / 7304 / 7305 / 10304 は暫定。NIP 登録の確認が必要 |
| テスト | 単体 + 障害注入できる模擬リレー（NIP-77 対応）での統合テスト + 公開リレーでの疎通確認（`npm run smoke:public`） |

## 11. Evolu との関係

anoDB は Evolu のコードを含まない（MIT、https://github.com/evoluhq/evolu）。セル単位 LWW・HLC・ローカル SQLite を正とする方針・Kysely の採用は Evolu に学んだ。Negentropy の実装は nostr-tools（Unlicense）を移植し、応答側を追加した。
