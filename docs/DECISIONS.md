# anoDB 設計決定ログ（v0.2〜v0.4）

> 2026-11-10 の grill-me セッションで確定。方針: **既定は最も強いセキュリティ**。
> 根拠と詳細は [DESIGN.md](DESIGN.md)、ワイヤフォーマットは [../PROTOCOL.md](../PROTOCOL.md)。

| # | 論点 | 決定 |
|---|---|---|
| 1 | 共有モデル | **グループ鍵（暗号化）＋各メンバー自身の鍵で署名＋メンバー表で権限検証** |
| 2 | 変更イベントの署名者 | **端末鍵**。本人の鍵（identity）は「この端末鍵は私の代理」という委任に一度だけ署名 |
| 3 | 本人の鍵の保存（既定） | **端末のセキュアストレージで暗号化保存**。オプションで「端末に残さず復元用キーとして一度だけ渡す」(`identity: 'recovery'`) |
| 4 | Node での鍵 | **環境変数が既定**（Node は主用途ではない） |
| 5 | `.env` の中身 | `ANODB_DEVICE_KEY` と `ANODB_DELEGATION` のみ。本人の鍵は入れず、復元用キーとして表示するだけ |
| 6 | `npx @anodb/cli init` | 対話式。環境 → フレームワーク → ドライバ → appId → 鍵 → リレー（疎通確認）→ ファイル生成。ブラウザ等ではエンドユーザー端末で鍵生成、init で鍵を作るのは Node のみ |
| 7 | init の言語 | 最初に 日本語 / English を選ぶ。**対話表示だけ**に反映（コード・エラー・ドキュメントは対象外） |
| 8 | 個人データ | **メンバー1人のスペース**として統一。スキーマは全スペース共通、各行は1スペースに属する |
| 9 | 役割 | **owner(1) / admin / writer / reader**、スペース単位 |
| 10 | 権限の衝突 | 同格同士の同時削除は**両方有効**、上位ロールが優先。削除時に**端末ごとの通し番号のカットオフ**を含め、それ以降の書き込みは拒否（衝突時は小さい方） |
| 11 | 新メンバー / 鍵更新 | 新メンバーには**現在状態のスナップショットのみ**（過去の鍵は渡さない）。グループ鍵は**削除・端末失効・追加・30日ごと**に更新 |
| 12 | メタデータ | **二重封筒**（外側は使い捨て鍵で署名、中で端末鍵署名）＋**世代ごとに変わる秘密由来のタグ**が既定。`metadataProtection: 'none'` で無効化可 |
| 13 | 招待 | **npub＋鍵パッケージ**と、**承認必須・使い捨て・期限付きリンク / QR** の両方。招待された側は承諾しないと参加しない |
| 14 | 端末追加 / 全端末紛失 | **QR ペアリング**（本人の鍵はコピーしない）。グループ鍵は端末鍵宛てのみ → **全端末紛失で個人スペースは永久に失われる** |
| 15 | 署名者 | **NIP-07 / NIP-46 / NIP-55** を共通 `Signer` で。公開イベントは本人の鍵で署名（recovery モードでは署名者が必要） |
| 16 | 公開データ | スキーマで**公開テーブル**を宣言（kind 0/1/3/7/30023 プリセット）。書き込みも `insert` |
| 17 | 型安全 SQL | **Kysely** の SQL ライク API に一本化（非同期）。生 SQL の書き込みは**トリガーで捕捉**して同期。旧 table API は廃止 |
| 18 | 同期 | **NIP-77 → 時刻ベースのフォールバック → 通し番号による欠落検出 → スナップショット**の4層 |
| 19 | 古いイベント | スナップショットは自動作成。NIP-09 削除依頼は既定オフ（`pruneOldEvents: true` で有効） |
| 20 | リリース | v0.2 土台 → v0.3 共有 → v0.4 同期と公開。v0.1 互換は捨てる（protocol v2） |
| 21 | 大きなファイル（2026-11-10 追加） | **Blossom** に端末側で暗号化して保存し、参照だけを DB に。複数サーバーへミラー、ハッシュ検証、ファイルごとの使い捨て鍵で認可（アップロードした端末だけ削除可）。暗号文を拒否するサーバーを Content-Type の偽装で回避することはしない |
| 22 | 通信経路（2026-11-10 追加） | **WebRTC を主、リレーを予備**に。シグナリングは Nostr リレー（nostr-p2p、public 化）。既定は**自分の端末同士だけ**直接接続、他メンバーとは `p2p.mode: 'members'` で（IP が見えるため）。全端末が ack したときだけリレー保存を省く |
| 23 | 型と UI（2026-11-10 追加） | Kysely の結果は **boolean → true/false、json → 値**（クエリの構文木から列の型を解決。生 SQL は SQLite の値のまま）。共有・端末追加の **React 部品を同梱**（`<PairDevice />` など）。リンクと QR は `https://アプリ/#anodb=…` で、開いても**クリックなしでは承認しない**・ペアリングは必ずコード照合 |
| 24 | 行の所有権（2026-11-12 追加、**25 で既定を変更**） | **行は作った人のもの**を既定に。行 ID に作成者の identity を埋め込み（`<pubkey>-<乱数>`）、全端末が受信時に「その行を変えられるのは作成者だけ（削除は owner / admin も可、編集は不可）」を検証。`createdBy` / `updatedBy` は署名から自動で埋まり偽装できない。共同編集の表は `shared()` で明示。**スナップショットは owner / admin（と自分の端末）からのものだけ信頼**（writer のスナップショットで他人の行を書き換えられた穴を塞ぐ）。HLC は書き手が選べるので「最初に作った人」を時刻で決める方式は採らない |
| 25 | 既定は普通の DB（2026-11-12 追加、**26 で撤回**） | **既定の保存先は「アプリ空間」**＝同じ appId の利用者全員で共有する 1 つの DB（招待なし・誰でも読み書き。鍵は appId から導出するので**実質公開**）。表も既定は**誰でも編集・削除可**（RLS なしの Postgres と同じ）。作成者だけが編集できる表は `owned()` で**オプトイン**（24 の規則）。`createdBy` の偽装防止（他人名義の行は作れない）だけは常に有効。自分専用の暗号化データは `space: db.personalSpace`（または `defaultSpace: 'personal'`）、招待制は従来どおり `createSpace`。アプリ空間にはメンバー・スナップショット・鍵更新がなく、端末失効は自分が知っている範囲でしか効かない。理由: DB として最初に触ったときに招待や承認が出てくるのはリッチすぎる |
| 26 | 暗号化された分散 DB に絞る（2026-11-15 追加） | 25 の**アプリ空間を削除**（鍵が appId から誰でも作れ、暗号化が名ばかりだった）。**公開テーブル（Nostr の投稿・プロフィール等を SQL 表に）と `db.nostr` も削除**（暗号化しない経路で、DB ではなく SNS クライアントの機能）。既定は**自分専用スペース**（自分の端末だけ・招待も規則も不要）。サーバーがない以上「読める＝鍵を持つ」なので、**共有＝鍵を渡す＝招待**は省けない。表は既定で誰でも編集可、`owned()` はオプトイン（25 から維持）。次: 招待を「本人確認・参加条件・鍵の受け渡し」に分け、外部の認証基盤（OIDC・NIP-05・独自発行者）を差し込めるようにする |
| 27 | 招待の仕方は anoAuth へ（2026-11-15 追加） | anoDB は**公開鍵だけ**を扱う: `addMember(space, npub, role, { devices? })`・`setRole`・`removeMember`・鍵の配布と更新。**招待リンク・参加申請・承認（`createInviteLink` / `requestJoin` / `approveJoinRequest`、`<InviteLink />` / `<JoinSpace />`）は削除**。誰を入れるか（リンク・承認・OIDC・署名付き証明書・外部 ID の予約・定期再確認）は別プロジェクト **anoAuth** が管理者の端末で判定し、`addMember` を呼ぶ。理由: 外部の認証基盤と連携させる前提で、DB に招待の方式を持ち込まない。grill の Q1〜Q7（pubkey＋外部 ID の予約 / 受付は owner・admin だけ / 入口は招待リンク / 証明付きリンクは何度でも＋期限 30 日＋取り消し / ID トークンは発行から 7 日 / 90 日ごとの再確認 / 初版はリンク・npub・手動承認・署名付き証明書・OIDC）は anoAuth に引き継ぐ |
| 28 | 一時イベント（2026-11-17 追加） | 入力中の表示などのために最小限の `db.emit(space, type, data)` / `db.onEvent(fn, { space, type })` を追加。保存も同期もしない（リレーにとっての ephemeral kind 27303）。スペースの鍵で暗号化し、端末の鍵で署名し委任つき → 受信側は送信者の identity が分かり、メンバー以外は送れない・読めない。60 秒より古いもの・8 KB 超は捨てる。WebRTC 経由の配送や既読管理などは上位（anoChat）に任せる |
| 29 | リレーの自動選定（2026-11-19 追加。⑥は **30 で変更**。段階①を 0.12.0 で実装） | 固定の 5 リレーをやめ、**検証済み候補（基準に合格したものすべて。数の目標はなく最低 20。運営元・ソフト・地域の偏りの上限は守る。2026-11-21 変更、当初は目標 100）から秘密を種に自動で選ぶ**。① 候補: 版番号つきの一覧を anoDB に同梱（アプリが追加可）。スペースごとに管理者の署名つき設定で**版と一覧の中身を固定**し、更新も管理者が行う（同じスペースの全端末が必ず同じ候補を使う。Sybil 対策として誰でも登録できる一覧にはしない）。② 種: スペース（7303/27303・WebRTC の合図）は**エポック鍵**、受信箱は**端末の公開鍵**、招待リンク・ペアリングは**リンクの秘密**。`sha256("anodb/v2/relays/" + 種)` を使ったランデブーハッシュで候補に順位を付ける（目印とはラベルを分ける）。③ エポック交換: 書くのは今の鍵の組だけ、直前の組は猶予期間だけ点検（`relayGraceDays`、既定 7 日。全端末が新しいエポックで書き始めたら早めにやめる）。それより古い組は `repair()` のときだけ。外されたメンバーは新しい組の場所も分からない。④ 接続: 常時接続は開いているスペースだけ（上限 10 前後）、他は数分おきに接続→新着確認→切断。⑤ 落ちたリレー: 使うのは**上位 10 位まで**。書き込みは上から順に受け付けた 5 つへ（10 位まで足りなければ outbox に残す）。普段の読み込みは上位 5、点検では **6〜10 位も必ず見る**（書き手が戻らなくても届く保証）。連番の抜けは前後の時刻の範囲で上位 10 に問い合わせる。6〜10 位で見つけた人はそのまま上位 5 へ転送（日付が古いので保証ではなくおまけ）、書き手は戻ったら署名し直して上位 5 へ送る。⑥ 移行: **互換性を切る（protocol v3）**。既存スペースは次のエポック交換で移り、30 日間は旧固定リレーも点検する |
| 30 | 自動選定への移行は互換性を保って3段階で（2026-11-21 追加。29 の⑥を変更） | protocol v3 で互換性を切るのをやめ、**v2 のまま段階的に移る**。旧版は固定リレーしか見ず、知らない種類のメッセージを捨てる（連番の抜けに見える）ので、合図は既存メッセージの任意項目にする。**段階①（0.12.0）**: 固定リレーに加え、購読している目印（スペースの各エポック・自分の受信箱・ペアリングの秘密）を自動で選んだ上位 5 個にも書き、両方から読む。届いたかの判定は固定リレーだけで行い、自動の側は追加の写し（つながっていなければ、つながった時に送る。NIP-77 の照合でも補う）。自動選定に対応した端末はスペースのメッセージに `rp: 1` を付ける。`relays` を指定したアプリは固定のまま（`autoRelays: true` で有効）。追加の接続は `maxAutoRelays`（既定 20）まで。候補は同梱の版 1（337 個、`RELAY_CANDIDATES`、仮）。**段階②（未実装）**: スペースの有効な全端末が `rp: 1` を付けたら、管理者の端末が**自動で**切り替えの印を出し、次のエポックから自動で選んだリレーだけに書く。固定リレーは 30 日読み続ける。候補の版と中身は切り替えの時に管理者の署名つき設定で固定する。29 の⑤（6〜10 位の点検・時刻範囲での抜け探し・転送）と④（開いていないスペースは数分おきに接続）もここで入れる。**段階③（未実装）**: 旧版の端末がいなくなったら固定リレーをやめる。受信箱と招待・ペアリングのリンクは③まで常に固定リレーにも書く |
| 31 | Postgres（PGlite）に対応（2026-11-25 追加） | サーバー側で Prisma などと同じ DB を使えるよう、**PGlite ドライバ**を追加。PGlite には同期 API がないので**ストレージ層を全面的に非同期化**し、原子性は「全ステートメントを 1 つのロックで直列化し、トランザクションは終わるまでロックを保持」で保つ（SQLite ドライバは同期のまま内部で包む）。共有の接続に他者の文が割り込まないよう、ドライバの `transaction()`（PGlite の排他ロック）を使う。表は Postgres のネイティブ型（boolean / bigint / double precision / jsonb）。**anoDB を通さない書き込み（Prisma 等）も同期する**: 永続トリガーが `anodb.mode` 設定で自分の書き込みと区別し、他者の書き込みは `anodb_ext` に積んで NOTIFY → anoDB が自分の書き込みと同じ検査・署名・暗号化で確定、通らない行はセルから復元して `'rejected-write'` を通知。anoDB が作っていない同名テーブルは消さずに起動を拒否。`spaces()` など UI が同期で読む小さな表はメモリにも持つ |
| 32 | サーバー確定テーブル（2026-11-26 追加） | 予約・在庫など一か所で確定させたい書き込みのため、**`confirmed(def, { by })`** を追加。その表に書けるのは指定した ID（サーバー）だけで、全端末が受信時に検証する（ロールに関係なく、スペースの owner でも不可）。スナップショットは `by` を書き直せるので、確定表のセルは**確定主体自身が署名したスナップショットだけ**から受け入れる。端末は通常の表（`owned` 推奨）に申請を書き、サーバーの **`serveRequests`** が申請を 1 件ずつトランザクションで判定し、結果（id = 申請 id）を**同じコミットで**申請と同じスペースへ書く（再起動しても二重に判定しない）。受信者ごとの絞り込みは新しい仕組みを作らず、既存のスペースで行う（本人とサーバーの非公開スペースに結果、サーバー所有の公開スペースに残枠）。外部 PostgreSQL の論理デコーディング連携は別途。 |
