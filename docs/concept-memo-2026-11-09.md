# NoDB 構想・アーキテクチャ検討メモ

> 作成日: 2026-11-09  
> ステータス: **構想・検証前**。本資料はこれまでの議論を整理したものであり、採用技術やAPIの確定仕様ではない。

## 1. 目標・コンセプト

**NoDB = No Database Provisioning**（仮称）。

アプリ開発者が、自前のAPIサーバーやDBサーバーを構築・運用せず、SDKを導入するだけで、ローカル保存、オフライン操作、複数端末同期、他ユーザーの公開データ取得、必要に応じた暗号化・共有を利用できるようにする。

- 「DBが存在しない」という意味ではない。各端末ではSQLiteなどのローカルDBを利用する。
- 「サーバーが一切存在しない」という意味でもない。Nostr Relayや必要に応じてBlossomなどの外部インフラを利用する。
- 原則は**アプリ専用バックエンドのプロビジョニング不要**。ただし公開Relayで保存の永続性、検索の網羅性、可用性は保証されない。
- Firebase / Supabase に近いSDK体験を、Local-firstと既存分散ネットワークで実現する構想。

> 名称上の注意: 「NoDB」は既存の別プロジェクトでも使われているため、名称の独占性や新規性は別途調査する。SupabaseはNoSQLではなくPostgreSQLベースのBaaSである。

## 2. 問題設定

従来のアプリは、クライアント → APIサーバー → DBサーバーという構成をとることが多い。BaaSならサーバーの実装・運用負荷は減るが、プロジェクト作成、バックエンド設定、ベンダーへの依存が残る。

NoDBは以下を狙う。

1. データをまずローカルSQLiteに保存し、オフラインでも読み書きする。
2. 変更を署名付きイベント／変更ログに変換し、リレーを通じて複製する。
3. 別端末では変更ログを検証・必要なら復号・マージし、ローカルDBへ反映する。
4. 他人の公開情報は、公開鍵やRelay Listなどからネットワーク上で発見し、ローカルDBへ取り込む。
5. 開発者には一貫した型付きのデータ操作APIを提供する。

## 3. 既存技術と担当範囲

| 技術 | 主な役割 | 補足 |
|---|---|---|
| SQLite | ローカル状態・SQL・索引・実体化ビュー | 端末側で検索可能。ただし未取得の世界中のデータまでSQL検索できるわけではない |
| Evolu | Local-first、型付きSQL、変更履歴、同期、E2EE、Owner単位の共有などの先行実装 | 仕組み・コード再利用の第一候補 |
| Nostr | 署名付きイベント、公開鍵アイデンティティ、Relayによる保存・配送、公開データ交換 | 任意のSQL、永続保存、アプリ独自権限を保証するDBではない |
| NIP-01 | Nostrイベントの取得・購読・配信の基礎 | フィルタ等を利用 |
| NIP-65 | ユーザーの利用Relayの発見 | 網羅的な検索インデックスではない |
| NIP-77 Negentropy | 互いが持つイベント集合の差分照合 | イベント本文転送や競合解決そのものは別実装。対応しないRelayもある |
| EvoluのRBSR | Evolu側の差分同期の仕組み | NIP-77と思想は似るが、そのまま互換ではない |
| nostrdb / strfry 等 | Nostrイベントの保存・インデックス | 汎用のアプリDBスキーマやSQLを提供するとは限らない |
| Blossom | 画像や動画などのblobの保管候補 | 永続性と利用規約は提供サーバー次第 |
| Iroh Docs | 署名エントリと実データの分離という参考設計 | ハッシュ参照＋blob分離のヒント |
| Autobase | 複数署名ログから決定論的なビューを構築する参考設計 | 順序の一致だけでは業務上の強整合性は得られない |

## 4. EvoluとNoDB構想の比較

| 機能 | Evolu | NoDBの目標 |
|---|---|---|
| Local-first | 実装済み | 継承・維持 |
| ローカルSQLite | 実装済み | 継承・維持 |
| 型安全なSQL | 実装済み | 継承・維持 |
| オフライン操作 | 実装済み | 継承・維持 |
| 競合解決 | カラム単位のLWW等 | 維持し、必要に応じてデータ型別のマージ方針を拡張 |
| E2EE | 実装済み | 維持・拡張 |
| 複数Relay | 利用可能 | Nostrを含む複数宛先をサポート |
| 他ユーザーとの共有 | Owner共有の仕組みあり | 維持・拡張 |
| 同期 | Evolu固有プロトコル / RBSR | Nostr NIP-01、可能ならNIP-77最適化 |
| 公開Nostr Relay利用 | ネイティブ対応ではない | 主要な目標 |
| Nostrの標準イベントとの相互運用 | ネイティブ対応ではない | kind 0プロフィール、kind 1投稿等を目標 |
| 公開データの発見 | Owner中心の同期とは別課題 | 公開鍵、タグ、リレー探索等をSDKで抽象化 |

**評価:** ローカルDBや暗号化・同期という基本技術はEvoluと大きく重なる。差別化は「既存Nostr Relayネットワークの活用」と「他ユーザーの公開データ発見・Nostr互換性」にある。単にEvoluのRelayをNostrに置き換えるだけでは独自価値は限定的。

## 5. 設計方針の変遷と現在の第一候補

### 検討した案A: 用途でエンジンを分ける

- Private / Shared → Evolu + Evolu Relay
- Public / Discovery → Nostr + Nostr Relay
- SDKで表面上のAPIを統一

**長所:** 既存機能を短期間で組み合わせやすい。  
**短所:** 内部で2系統のDB・変更履歴・同期方式を管理するため、一貫したトランザクション、JOIN、公開への切り替えが複雑になる。

### 現在の第一候補・案B: 単一ローカルDBエンジン＋Nostr同期

```text
┌─────────────────────────────────────┐
│         Application (TS/React)      │
└─────────────────┬───────────────────┘
                  │ CRUD / SQL / subscribe
┌─────────────────▼───────────────────┐
│             NoDB SDK                │
│  - Schema / typed query             │
│  - Identity / signing / E2EE        │
│  - Change log / merge policy        │
│  - Outbox / retry / projections     │
│  - Discovery / permissions          │
│             SQLite                 │
└─────────────────┬───────────────────┘
                  │ transport abstraction
┌─────────────────▼───────────────────┐
│         Nostr Transport             │
│         NIP-01 / NIP-77*            │
└─────────────────┬───────────────────┘
                  │
       Existing Nostr Relays

* NIP-77は対応Relayのみ。非対応時は別の取得・同期手段が必要。
```

基本方針:

1. **アプリから見えるDBエンジンは一つ**。ローカルSQLite、クエリ、変更ログ、競合解決を統合する。
2. EvoluのローカルDB・同期・暗号化・共有の設計と実装を最大限参考にする。
3. ネットワーク接続はNostrを第一級のTransportとして扱う。
4. プライベートデータは暗号化したNoDB専用イベントで同期し、公開プロフィール・投稿は可能な限り標準Nostrイベントに対応する。
5. 専用リレーなどへのTransport追加は拡張可能にする。ただし**既存Evolu Relayとの互換は自動では成立しない**。

**重要:** 「単一エンジン」は目標であり、Evoluのコードをフォークすれば直ちに実現できるわけではない。Evoluの内部データモデル・プロトコル・公開イベント非対応を解きほぐす必要がある。

## 6. 基本的なデータフロー

### 6.1 書き込み

1. アプリがSDK経由でデータを更新。
2. SDKがローカルSQLiteの状態・変更ログ・Outboxを適切にトランザクション管理。
3. 変更をNostrイベントにエンコードする。所有者や署名者、スキーマバージョン、マージに必要なメタデータを含める。
4. 非公開データは暗号化し、Nostrイベントへ署名する。
5. Relayへ送信。複数Relayへの成功確認と失敗時の再送をSDKが担当。
6. リレー受領と**永続的な保存保証は別**として扱う。

### 6.2 オフラインの他ユーザーのプロフィール取得

1. 閲覧者のローカルSQLiteにキャッシュがあれば即表示。
2. SDKが相手の公開鍵を使い、既知のRelayやNIP-65 Relay Listなどを探索。
3. 保存済みプロフィールイベントがRelayにあれば取得する（相手本人のオンライン状態は不要）。
4. イベントの署名・形式・更新順を検証し、ローカルSQLiteへ投影。
5. キャッシュの鮮度や同期状態をSDKが公開する。

**取得不能なケース:** どのRelay・端末にもコピーがない、利用できるRelayが分からない、リレーがイベントを消した、アクセス権がない、など。

### 6.3 リアルタイム更新と再接続

- オンライン: NIP-01の購読で新しいイベントを受信してSQLiteへ反映。
- 再接続: 保存済みイベント集合とRelay側の差分を取得。NIP-77対応ならNegentropyで照合し、イベント本文を別途取得。
- NIP-77非対応Relay向けにNIP-01等のフォールバックを設計。
- 更新の欠落、Relayごとの保存差、ログの削除・圧縮に対応するため、スナップショットや修復手順を別途設計。

## 7. イベントモデルと競合解決

- **変更履歴:** CRDT/操作履歴が必要なデータは、古い履歴が捨てられ得るNostr replaceable eventだけに依存しない。通常の保存イベント、スナップショット、圧縮／GC戦略を検討する。
- **LWW:** ユーザー名、単純な真偽値などに適用しやすい。時計の扱い、同時更新時のタイブレークを決定論的に定義する。
- **集合・カウンター:** いいね・フォロー関係では、単一の数値更新より操作やユーザー別レコードを集約する方式を検討する。
- **共同編集テキスト:** 必要であれば専用のテキストCRDTを導入する。
- **不変条件:** 残高・在庫・一意性など、全世界で強い整合性を要求する用途では協調的な権威主体が必要になる場合がある。

Nostrイベントの署名とCRDTのマージは別責務。署名が有効でも、その更新がアプリの権限ポリシー上有効とは限らない。

## 8. 公開・非公開の両立

| データ | 想定イベント | 保護方式 |
|---|---|---|
| 個人メモ・下書き | NoDB独自イベント | E2EE |
| 限定共有ルーム | NoDB独自イベント | グループ鍵・権限検証 |
| 公開プロフィール | 標準kind 0等 | 公開、署名検証 |
| 公開投稿 | 標準kind 1等 | 公開、署名検証 |
| 任意のアプリ公開レコード | 専用kindや既存NIPに沿った形式 | 公開、署名検証 |

- Nostrの署名は**認証・改ざん検証**であり、秘密保持は提供しない。
- 既存のNostrクライアントとの互換性を求めるイベントは、標準形式を保つ。
- 非公開データを公開する操作は、公開用イベントを別途生成する。公開後に「取り下げ」ても第三者が保存したコピーの消去は保証できない。
- 共有相手のアクセス権を後から取り消しても、過去に渡した平文や暗号化鍵を完全には回収できない。

## 9. クエリとデータ発見の境界

```ts
// 仮のSDK API。実在するAPIではない。
const db = createNoDB({ schema });

await db.todos.insert({ title: '買い物' });
const todos = await db.todos.findMany(); // 取得済みのローカルデータ
const profile = await db.profiles.getByPubkey(pubkey); // 必要ならRelay探索
```

- ローカルSQLは取得済みのローカルデータにしか適用できない。
- NIP-01フィルタは任意SQLや任意フィールドのグローバルな範囲検索ではない。
- 全ユーザーの年齢検索などには、検索用インデックスサービスや追加の集約が必要になり得る。
- 将来のAPIでは `local / syncing / synced / stale / unavailable` 等の状態を扱う。

## 10. NoDBのメリットと残るリスク

### 期待できるメリット

- プロジェクトごとのDB・APIサーバーが不要な状態から開発を始められる。
- オフラインで読み書きでき、起動時やネットワーク復帰時に同期できる。
- 特定のクラウドDBサービスへの依存を減らせる。
- Nostr公開鍵、Relay、既存イベントを介してデータを発見・交換できる。
- SDKから型付きの統一APIを提供できる。

### 未解決／要検証

| 課題 | 対応案・限界 |
|---|---|
| データ永続性 | 複数Relay、保存確認、任意の有料/専用保存先。ただし無料の永久保存は保証不能 |
| Relay間の差分 | NIP-77、フォールバック同期、スナップショット、修復 |
| 削除 | TombstoneやGCポリシー。取得済みコピーの完全削除は保証不能 |
| アクセス制御 | 署名付き権限ルール、各クライアントの検証、鍵配布・ローテーション |
| グローバル検索 | 外部インデックス、タグ設計、検索範囲の明示 |
| 競合解決 | フィールドごとのLWWから開始し、必要な型のみCRDT拡張 |
| トランザクション | ローカルACIDはSQLiteで可能。全端末・全Relayでの原子的コミットは別問題 |
| スパム・濫用 | イベントサイズ、レート、配信先リレーのポリシー、署名・検証 |
| スケーラビリティ | イベント数増加時の同期・インデックス・GC・帯域コストを計測 |
| Evoluとの互換性 | 内部プロトコルの結合度、コード再利用箇所、移植コストを調査 |

## 12. 推奨する検証順序

1. **Evoluコード調査**: SQLite/スキーマ/変更ログ/暗号化/Relay通信の境界を把握。フォーク改造が現実的か確認。
2. **最小PoC**: 2端末でSQLiteへのローカル書き込み→独自Nostrイベント発行→Relay保存→受信・再構築。まずLWWだけで成立させる。
3. **オフライン検証**: 片側をオフラインにし、復帰後の欠落補完、イベント順序シャッフル、重複配送、Relay停止を試す。
4. **公開イベント互換**: kind 0プロフィールやkind 1投稿を既存Nostrクライアントから読み書き可能にする。
5. **E2EE・共有**: 所有者／参加者の鍵と権限モデルを実装し、権限取り消しの限界を定義。
6. **高信頼化**: 複数Relay、NIP-77、スナップショット、GC、Blossom、観測性を追加。

## 13. まだ確定していない設計判断

- Evoluを直接フォークするか、設計を参考に新規実装するか。
- Evolu Relay互換を保つか、Nostrに特化するか。
- 変更ログをNostrイベントにどの粒度で載せるか（1フィールド／1トランザクション／バッチ）。
- スキーマ進化と古いクライアントの扱い。
- 公開Nostr標準イベントと独自DBイベント間の双方向変換の範囲。
- データ発見時のリレー探索とキャッシュの整合性。
- Relayが保存しない場合の品質保証・商用運用モデル。

## 14. 暫定結論

**NoDBは「EvoluのようなLocal-first DB体験を、Nostrの分散公開ネットワークに接続するSDK」を目指す。** ただし、一つのDBエンジンに統合する案はまだ設計仮説であり、Evoluの実コードにどこまで手を入れる必要があるかは未検証。

最大の価値候補は、(1) DB/バックエンドのゼロプロビジョニング、(2) オフライン対応、(3) 他ユーザーの公開データ発見、(4) Nostrイベントとの相互運用を、アプリ開発者から一貫したAPIとして扱えること。

最大の技術的障害は、**Nostrリレー上の欠落し得るイベントを用いた正確な複製・修復、権限/暗号化、強い永続性を持たないことによるプロダクト上の限界**である。
